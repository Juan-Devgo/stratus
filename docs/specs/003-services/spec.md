# Services

## 1. Metadata
- Status: Approved
- Updated: 2026-10-22
- Constitution version: 2.0.0
- Required by: none

## 2. Constitution relationship
- Applies:
  - P1: the backend only validates input (including the uploaded archive's size and extension), invokes one script per operation and reports the result; transfer, extraction, user creation, unit files and systemctl run only in scripts.
  - P2: each operation has its own script file with `set -euo pipefail`, explicit arguments and a documented exit-code table; the archive and the environment variables reach the scripts as paths of temporary host files given as arguments (REQ-12, REQ-13).
  - P3: name, description, executable, arguments, Restart, RestartSec and every environment key and value are validated against an allowlist in the UI, in the backend and in the script, and passed as discrete arguments.
  - P4: every operation, including the file transfer, runs over SSH as root with the backend key against the VM's IPv4 (001 REQ-24).
  - P5: no private key is created or handled by this module; environment values are secrets with the same never-logged rule (REQ-13).
  - P6: every operation ends with a success or failure message; the history keeps command, exit code, stderr and timestamp of every change and every failed read, without environment values (REQ-27).
  - P7: the home card "Servicios systemd" opens one screen for the module; forms confirm the result.
  - P8: each script runs on its own with bats tests; a before/after demonstration on a real VM covers what stubs cannot (AC-31, AC-32).
  - P9: reuses the VM selector, script runner, operation runner, per-VM locks, history and redaction of 001/002; no new abstraction beyond the module's operations.
- Conflicts: none. P2 vs secrets in argv resolved as in 002: environment values are written to a temporary secret file whose path is the argument.

## 3. User stories
| ID | Priority | Actor | Story |

| US-2 | P1 | Student admin | As a student admin, I need to see the services created by the app on the selected VM with their active and enabled state, so I know what runs |

## 4. Requirements
- REQ-1 (US-1): The create form has: service name, description, application archive, executable, executable arguments, Restart, RestartSec and a list of environment variable rows (key, value).
- REQ-2 (US-1): The service name must match `^[a-z][a-z0-9-]{0,31}$`; if the VM already has a systemd unit `<name>.service` (any origin, for example `ssh`), a user or a group with that name, or the path `/opt/<name>` or `/etc/<name>.env` already exists, creation is rejected with "Ya existe un servicio o usuario con ese nombre en la VM" and nothing changes on the VM.
- REQ-3 (US-1): The description is 1 to 100 printable UTF-8 characters (accents and ñ allowed) without `%`, `\`, `"`, line breaks or other control characters.
- REQ-4 (US-1, US-6): The archive is one `.tar.gz` file uploaded from the browser, at most 200 MB; a larger file is rejected with "El archivo supera 200 MB" and a file without the `.tar.gz` extension with "El archivo debe ser .tar.gz", both before any script runs and with nothing uploaded to the VM.
- REQ-5 (US-1, US-6): The archive's content is extracted directly into `/opt/<name>`; an archive that is not a valid gzip tar, or holds an absolute path, a `..` segment, a symlink, a hard link or a device or other special file, is rejected with "Archivo comprimido inválido" and nothing changes on the VM.
- REQ-6 (US-1, US-5, US-6): The executable is a path relative to `/opt/<name>` matching `^[A-Za-z0-9._-]+(/[A-Za-z0-9._-]+)*$` without `.` or `..` segments, at most 255 characters, and must be a regular file in the archive (create, redeploy) or in `/opt/<name>` (edit); otherwise the operation is rejected with "El ejecutable no existe en el directorio de la aplicación" and nothing changes. The executable gets execute permission for its owner.
- REQ-7 (US-1, US-5): The executable arguments are optional: up to 16 tokens separated by single spaces, each matching `^[A-Za-z0-9._/:=,@+-]{1,128}$`; the unit's `ExecStart` is `/opt/<name>/<executable>` followed by those tokens.
- REQ-8 (US-1, US-5): Restart is one of `no`, `always`, `on-failure` (default `on-failure`); RestartSec is an integer 0-3600 (default 5).
- REQ-9 (US-1, US-5): Environment variables: 0 to 50 rows; keys match `^[A-Z_][A-Z0-9_]{0,63}$` and are unique; values are 0 to 1024 printable ASCII characters (space to `~`) without line breaks; the service sees each value exactly as typed.
- REQ-10 (US-1): Creating a service, in one operation: creates the system user and group `<name>` with home `/opt/<name>` and shell `/usr/sbin/nologin`; extracts the archive into `/opt/<name>` owned recursively by `<name>:<name>`; writes `/etc/<name>.env` (mode 600, owner `root:root`) with the variables; writes `/etc/systemd/system/<name>.service`; runs daemon-reload and enables and starts the service.
- REQ-11 (US-1, US-5, US-6): The unit file holds a marker comment identifying it as created by the app, plus: `[Unit]` with `Description=<description>` and `After=network.target`; `[Service]` with `Type=simple`, `User=<name>`, `Group=<name>`, `WorkingDirectory=/opt/<name>`, `EnvironmentFile=/etc/<name>.env`, `ExecStart` (REQ-7), `Restart`, `RestartSec`, `NoNewPrivileges=true`, `ProtectSystem=strict`, `ProtectHome=true`, `PrivateTmp=true`, `ReadWritePaths=/opt/<name>`; `[Install]` with `WantedBy=multi-user.target`. Only description, executable, arguments, Restart and RestartSec vary.
- REQ-12 (US-1, US-6): The backend stores the uploaded archive in a temporary host file passed to the script as an argument and deletes it when the operation ends, success or failure.
- REQ-13 (US-1, US-5): Environment variables reach the script as the path of a temporary host secret file (mode 600) given as an argument, deleted when the operation ends, success or failure; values never appear in argv, the history, logs, script output, the list, or the UI after submission; the UI masks value fields while typing.
- REQ-14 (US-1): A creation that fails after the first change on the VM removes everything it created (unit, env file, `/opt/<name>`, user and group, and runs daemon-reload), so no partial service remains. If that cleanup also fails, the script exits with its own code, the UI shows "No se pudo crear el servicio <name> y la limpieza falló; revise la VM" and the history stderr records both errors.
- REQ-15 (US-1, US-6): A creation succeeds when every step of REQ-10 succeeds, even if the application then exits, and the service stays installed. About 3 seconds after start the active state is read and shown in the UI; any state other than `active` (for example `failed` or `activating (auto-restart)`) is shown as a warning pointing to Estado and Logs.
- REQ-16 (US-2): The module screen uses the VM selector of 001 (REQ-2) and lists only units that hold the app's marker, read from the VM at each load and after each operation, with name, description, active state (as reported by systemd, for example `active`, `inactive`, `failed`), enabled state (`enabled` or `disabled`), Restart and RestartSec. A successful list shows the toast "Lista de servicios actualizada"; a failed list shows the usual failure message.
- REQ-17 (US-3): Each listed service has buttons Iniciar, Detener, Reiniciar, Habilitar and Deshabilitar, each running its systemctl action; an action that leaves the state unchanged (for example starting an active service) succeeds. After Iniciar or Reiniciar succeeds, the active state is read and shown with the same timing and warning as REQ-15.
- REQ-18 (US-3..US-7): Every operation on an existing service accepts only units that hold the app's marker; a request for another unit (for example `ssh`) or a missing one is rejected with "Solo se pueden gestionar servicios creados por Stratus" and nothing changes.
- REQ-19 (US-4): Each listed service has an Estado button that shows the output of `systemctl status <name>` in a panel; an inactive or failed service is shown, not treated as an operation failure.
- REQ-20 (US-4): Each listed service has a Logs button that shows the last 100 lines of the service's journal on demand; there is no live follow.
- REQ-21 (US-5): The edit form is prefilled with the current description, executable, arguments, Restart and RestartSec read from the VM, and shows the current environment keys without values; the name cannot be changed.
- REQ-22 (US-5): The edit form has a "Reemplazar variables de entorno" checkbox, unchecked by default; unchecked, `/etc/<name>.env` stays as is; checked, the user enters every variable again (keys prefilled, values empty) and the file is rewritten completely with them.
- REQ-23 (US-5): Saving an edit rewrites the unit file, rewrites the env file per REQ-22, runs daemon-reload and restarts the service only if it was running (`active` or `activating`, for example `activating (auto-restart)`); the enabled state is unchanged. Before rewriting, it backs up the unit file and `/etc/<name>.env` on the VM; if a rewrite, daemon-reload or the restart command fails, both files are restored, daemon-reload runs, the previous active state is restored, and the backups are deleted when the operation ends. An application that restarts and then exits counts as success, with the same state reading and warning as REQ-15.
- REQ-24 (US-6): The redeploy form has the new archive (REQ-4, REQ-5) and the executable (REQ-6), prefilled with the current one; the executable must be a regular file in the new archive. Redeploy runs for an existing service after a confirmation warning that the whole content of `/opt/<name>` is replaced, including data files; it stops the service if it is running (`active` or `activating`, for example `activating (auto-restart)`), replaces the content of `/opt/<name>`, restores ownership, rewrites the unit's `ExecStart` (keeping the current arguments) and runs daemon-reload if the executable changed, and starts the service again only if it was running. Before replacing, it backs up the current content of `/opt/<name>` and the unit file on the VM; if extraction, ownership, the unit rewrite, daemon-reload or the start command fails, the previous content, the previous unit file (followed by daemon-reload) and the previous active state are restored, and the backups are deleted when the operation ends. A new application that starts and then exits counts as success, with the same state reading and warning as REQ-15.
- REQ-25 (US-7): Each listed service has a delete button that opens a confirmation dialog naming the service; after confirming, the service is stopped and disabled, and the unit file, `/etc/<name>.env`, `/opt/<name>`, the user and the group `<name>` are removed, followed by daemon-reload. The unit file is removed last, so if any step fails the service stays listed and delete can be run again; each step tolerates parts that are already gone (for example an already stopped service or a missing env file). A failed delete shows a failure message naming the service.
- REQ-26 (US-1..US-7): Every operation runs over SSH as root with the backend key against the VM's IPv4 (001 REQ-24, REQ-29), is executed by its own script file with a 15-minute timeout (001 REQ-14) and follows the one-operation-per-VM rule (001 REQ-15).
- REQ-27 (US-8): Create, edit, redeploy, delete, start, stop, restart, enable and disable are always recorded; list, status and logs are recorded only when they fail. Each row has operation name, VM, command and arguments, exit code, stderr, result and timestamp; environment values are never recorded.
- REQ-28 (US-8): The module screen shows the last 50 recorded operations of the module; each row can expand to show its stderr.
- REQ-29 (US-1..US-7): Every operation ends with a success or failure message in the UI; failure messages are understandable and do not show raw stack traces; while an operation runs, the UI shows a loading indicator and disables the buttons.
- REQ-30 (US-1..US-8): The home card "Servicios systemd" is enabled and navigates to the module screen (supersedes the "Próximamente" state of 001 REQ-19 for this card only).
- REQ-31 (US-1..US-7): Each script file starts with a header documenting usage, arguments and exit-code table (including reserved code 99 "Operación no implementada"), followed by `set -euo pipefail`, with comments organized in sections and numbered steps.
- REQ-32 (US-1..US-8): The UI is built with shadcn/ui components and all its text is in Spanish.

## 5. Acceptance criteria
- AC-1 (US-1): Given name `demian-lee`, a valid archive holding `demian-lee`, `templates/`, `static/` and `data/`, executable `demian-lee`, Restart `on-failure`, RestartSec 5 and variables `PORT=8080`, `SERVER_NAME=Servidor-Produccion-1`, `ADMIN_PASSWORD=Secreta123`, when the user submits, then the create script is invoked with each value as a separate argument and file paths for the archive and the variables, and the UI shows success and the state `active`.
- AC-2 (US-1): Given that creation, when the VM is inspected, then user `demian-lee` exists with home `/opt/demian-lee` and shell `/usr/sbin/nologin`, `/opt/demian-lee` and its files are owned by `demian-lee:demian-lee`, `/etc/demian-lee.env` is mode 600 `root:root` with the three variables, and the unit file holds the marker and every line of REQ-11.
- AC-3 (US-1): Given names `Demian`, `1app`, `app;rm`, `app_x`, an empty field or a 33-character name, when the user submits, then the UI and backend reject it and no script is invoked.
- AC-4 (US-1): Given the VM has unit `ssh.service`, user `www-data`, group `staff`, or (with no unit, user or group `api`) the directory `/opt/api` or the file `/etc/api.env`, when the user creates a service with that name, then the UI shows "Ya existe un servicio o usuario con ese nombre en la VM" and nothing changes on the VM.
- AC-5 (US-1): Given a 201 MB file or a file named `app.zip`, when the user submits, then the UI shows "El archivo supera 200 MB" or "El archivo debe ser .tar.gz", the backend rejects a direct API call the same way, and no script is invoked.
- AC-6 (US-1, US-6): Given an archive holding `../evil`, `/etc/passwd`, a symlink, or a corrupt gzip, when the user creates or redeploys, then the UI shows "Archivo comprimido inválido" and nothing changes on the VM.
- AC-7 (US-1, US-5, US-6): Given executable `bin/app` not present in the archive (create, redeploy) or in `/opt/<name>` (edit), or executable `../x` or `/bin/sh`, when the user submits, then the operation is rejected ("El ejecutable no existe en el directorio de la aplicación" or a validation error) and nothing changes.
- AC-8 (US-1, US-5): Given a description with `%`, `\` or a line break, arguments with `;`, `$` or `"`, more than 16 argument tokens, Restart `on-abort`, or RestartSec -1 or 3601, when the user submits, then the form shows a validation error and no script is invoked.
- AC-9 (US-1, US-5): Given variable keys `port`, `1PORT` or a duplicate key, a value with a line break or a non-ASCII character, a 1025-character value or 51 rows, when the user submits, then the form shows a validation error and no script is invoked.
- AC-10 (US-1, US-5): Given a variable value `a b "c" $HOME \x`, when the service runs, then its environment holds exactly that value.
- AC-11 (US-1, US-5): Given an operation with variable `ADMIN_PASSWORD=Secreta123`, when the history, logs, script output, process arguments, list response and edit form are inspected, then `Secreta123` does not appear and the temporary secret file no longer exists; the temporary archive file no longer exists either.
- AC-12 (US-1): Given a creation that fails after the user was created (for example, extraction fails), when it finishes, then the UI shows a failure and the unit, env file, `/opt/<name>`, user and group do not exist on the VM.
- AC-13 (US-1): Given a creation that fails and whose cleanup also fails, when it finishes, then the script exits with the cleanup-failure code, the UI shows "No se pudo crear el servicio <name> y la limpieza falló; revise la VM" and the history stderr holds both errors.
- AC-14 (US-1): Given an archive whose executable exits with code 1 at start, with Restart `no` or with Restart `on-failure` and RestartSec 5, when the service is created, then the operation succeeds, the service remains installed, and the UI shows the state read about 3 seconds after start (`failed` or `activating (auto-restart)`) with a warning pointing to Estado and Logs.
- AC-15 (US-2): Given a VM with app-created services `demian-lee` (active, enabled) and `api` (inactive, disabled) plus system units `ssh` and `cron`, when the user opens the module screen with that VM selected, then the table shows only `demian-lee` and `api` with their description, states, Restart and RestartSec, and the toast "Lista de servicios actualizada" appears.
- AC-16 (US-2): Given no VM selected, when the user opens the module screen, then the list is empty and the create button is disabled with a hint to select a VM.
- AC-17 (US-1..US-7): Given a powered-off VM, when the user runs any operation, then the UI shows "La VM no tiene dirección IP; verifique que esté encendida".
- AC-18 (US-3): Given service `api` inactive and disabled, when the user clicks Iniciar and then Habilitar, then `systemctl is-active api` is `active`, `systemctl is-enabled api` is `enabled` and the list shows both; when the user clicks Detener and Deshabilitar, then both revert; when the user clicks Reiniciar on an active service, then its main PID changes.
- AC-19 (US-3): Given service `api` active, when the user clicks Iniciar, then the operation succeeds and the state stays `active`.
- AC-20 (US-3..US-7): Given a direct API request for `ssh` or a missing service with any action, status, logs, edit, redeploy or delete, when it is processed, then it is rejected with "Solo se pueden gestionar servicios creados por Stratus" and nothing changes.
- AC-21 (US-4): Given service `api` failed, when the user clicks Estado, then the panel shows the `systemctl status api` output including `failed`, and the UI does not report an operation failure.

## 6. Out of scope
- Managing systemd units not created by the app (for example `ssh`, `nginx`).
- Renaming a service; changing its user, directory, unit type, `After`, `WantedBy` or hardening options.
- Archive formats other than `.tar.gz`, archives above 200 MB, and copying files from a host path.
- Live log streaming (`journalctl -f`) and log filtering.
- HTTP health checks of the application.
- Reading environment values back from the VM.
- Timers, sockets, user units and templated units (`name@.service`).
- Building or compiling the application.

## 7. Clarifications
- 2026-10-22. Q: How are the application files transferred? A: One `.tar.gz` uploaded from the browser, at most 200 MB, copied to the VM and extracted into `/opt/<name>`.
- 2026-10-22. Q: Which .service fields are editable? A: Description, executable (relative to `/opt/<name>`) with optional arguments, Restart (`no`, `always`, `on-failure`) and RestartSec (0-3600); the rest is fixed as in the example, hardening always on.
- 2026-10-22. Q: How is the secrets file handled? A: KEY=value rows, write-only; values travel in a temporary 600 file and never appear in history, logs, argv or output; `/etc/<name>.env` is 600 `root:root`; an edit rewrites the whole file and the UI shows only keys.
- 2026-10-22. Q: Which services does the module manage? A: Only those created by the app, recognized by a marker comment in the unit file, read from the VM at each load with name, active state and enabled state.
- 2026-10-22. Q: What do status and logs show? A: Estado shows `systemctl status` output; a separate Logs button shows the last 100 journal lines on demand, without live follow.
- 2026-10-22. Q: Which lifecycle operations besides create and the six actions? A: Edit configuration (rewrite unit and env, daemon-reload, restart if active), redeploy a new archive, and delete with confirmation removing unit, env, `/opt/<name>` and the system user.
- 2026-10-22. Q: Service name and system user rules? A: Name `^[a-z][a-z0-9-]{0,31}$`; the system user has the same name, home `/opt/<name>`, shell `/usr/sbin/nologin`; an existing unit, user or group with that name is rejected without changes.
- 2026-10-22. Q: What does create do, and what goes to the history? A: Create runs `enable --now` and the UI shows the resulting state, with no HTTP health check; create, edit, redeploy, delete and the five actions are always recorded; list, status and logs only when they fail.
- 2026-10-22. Q: In the edit form, how are environment variables handled when the user only changes something else (for example Restart)? A: A "Reemplazar variables de entorno" checkbox, unchecked by default; unchecked keeps `/etc/<name>.env` unchanged; checked, the user re-enters all variables and the file is rewritten completely.
- 2026-10-22. Q: When a create finishes but the application does not stay running, what happens? A: Create succeeds and the service stays installed; about 3 s after start the state is read, and any state other than `active` (for example `failed`, `activating (auto-restart)`) is shown as a warning pointing to Estado and Logs.
- 2026-10-22. Q: When a redeploy fails, what happens? A: The script backs up `/opt/<name>` on the VM before replacing it; if extraction, chown or start fails, it restores the backup and the previous active state, then deletes the backup; a new app that starts and then crashes counts as success, with the same warning as create.
- 2026-10-22. Q: On create, what if `/opt/<name>` or `/etc/<name>.env` already exists without a unit, user or group of that name? A: Create is rejected with "Ya existe un servicio o usuario con ese nombre en la VM" and nothing changes.
- 2026-10-22. Q: If delete fails partway, what happens? A: Delete can be retried: the unit file is deleted last, so the service stays listed and can be deleted again; each step tolerates parts already gone; the UI shows the failure naming the service.
- 2026-10-22. Q: If an edit fails partway, what happens? A: Before rewriting, the unit and `/etc/<name>.env` are backed up; on failure both are restored, daemon-reload runs, the previous active state returns and the backups are deleted; an app that restarts and then crashes counts as success with the REQ-15 warning.
- 2026-10-22. Q: Which fields does the redeploy form have? A: The archive plus the executable, prefilled with the current one; if changed, `ExecStart` is rewritten in the same operation (for example `bin/server`); the executable must exist in the new archive, otherwise the redeploy is rejected without changes; the rollback also restores the unit file and runs daemon-reload.
- 2026-10-22. Q: What does the UI show after Iniciar or Reiniciar on an app that crashes? A: The operation succeeds; about 3 s later the state is read and any state other than `active` is shown as a warning pointing to Estado and Logs, as in create, redeploy and edit.
- 2026-10-22. Q: For edit and redeploy, how is a service in `activating` state (for example `activating (auto-restart)`) treated? A: As running, the same as `active`: redeploy stops it before replacing `/opt/<name>` and starts it again at the end; edit restarts it.
