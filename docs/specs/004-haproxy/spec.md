# HAProxy load balancing

## 1. Metadata
- Status: Approved
- Updated: 2026-10-24
- Constitution version: 2.0.0
- Required by: none

## 2. Constitution relationship
- Applies:
  - P1: the backend only validates input, invokes one script per operation (create and delete load balancer, assign and remove server, save frontend, refresh IPs, read state) and reports the result; VirtualBox networks, adapters, haproxy.cfg and SSH keys of the jump account change only in scripts.
  - P2: each operation has its own script file with `set -euo pipefail`, explicit arguments and a documented exit-code table; scripts are idempotent where the operation allows it (refresh, save frontend, remove an already removed server).
  - P3: load balancer name, memory, CPUs, frontend port, server port and selected VM are validated against an allowlist in the UI, in the backend and in the script, and passed as discrete arguments.
  - P4: the load balancer is bootstrapped by Guest Additions as in 001 REQ-30 and afterwards reached only by SSH with the backend key at its bridged IP; servers are reached only by SSH with key authentication through a jump on the load balancer; the `jump` account accepts only keys and has no password.
  - P5: no private key is created by this module; private keys generated by 001 and 002 for a server keep their rules, and only public keys are copied to the `jump` account.
  - P6: every operation ends with a success or failure message; the history keeps command, exit code, stderr and timestamp of every change and every failed read.
  - P7: the home card "Backends HAProxy" opens one screen for the module; forms confirm the result.
  - P8: each script runs on its own with bats tests; a before/after demonstration on the real host covers what stubs cannot (AC-30, AC-31, AC-32, AC-33).
  - P9: reuses the VM creation, VM selector, script runner, operation runner, per-VM locks, history and redaction of 001-003; one frontend and one backend per load balancer.
- Conflicts: none with the constitution. This spec supersedes these requirements of the approved specs 001-003 for load balancers and assigned servers; the supersessions are declared only here and 001-003 stay unchanged:
  - 001 REQ-1 and AC-26 (single bridged adapter): superseded by REQ-10.
  - 001 REQ-2 (IPv4 shown for a VM): superseded by REQ-13.
  - 001 REQ-3 (delete): superseded by REQ-6 for load balancers and by REQ-12 for assigned servers.
  - 001 REQ-9 and 002 REQ-11 (key usage message): superseded by REQ-18.
  - 001 REQ-15 (one VM per operation lock): superseded by REQ-21.
  - 001 REQ-25 (package protections): superseded by REQ-5 for load balancers.
  - 001 REQ-24, 001 REQ-29, 002 REQ-17 and 003 REQ-26 (direct SSH to `<VM IPv4>:22`): superseded by REQ-19.
  - 001 REQ-19, 002 AC-27 and 003 AC-35 ("Próximamente" state of the HAProxy card): superseded by REQ-25.

## 3. User stories
| ID | Priority | Actor | Story |
|---|---|---|---|
| US-1 | P1 | Student admin | As a student admin, I need to create and delete load balancer VMs from a HAProxy base disk, each with its own internal network, so I can put servers behind them |
| US-2 | P1 | Student admin | As a student admin, I need to assign existing VMs as servers of a load balancer with their port, and remove them, so HAProxy distributes traffic to them |
| US-3 | P1 | Student admin | As a student admin, I need to set the frontend port of a load balancer, so clients reach the servers through it |
| US-4 | P1 | Student admin | As a student admin, I need the backend to follow the servers' DHCP addresses after every restart, so balancing keeps working without manual edits |
| US-5 | P2 | Student admin | As a student admin, I need to see each server's address, port and HAProxy health state, so I know which servers receive traffic |
| US-6 | P1 | Student admin | As a student admin, I need to reach servers by SSH through the load balancer with my key, so I can administer them although they are on an internal network |
| US-7 | P2 | Student admin | As a student admin, I need to see the history of operations of the module, so I can diagnose failures |

## 4. Requirements
- REQ-1 (US-1): The module screen has a "Crear balanceador" form with name, memory and CPUs, validated as in 001 REQ-1 (same regex, ranges, uniqueness among registered VMs and messages). The load balancer is a VM whose disk is a differencing disk on top of the multi-attach base disk at `APP_HAPROXY_BASE_DISK` (Debian 13 with Guest Additions, openssh-server and HAProxy installed with a basic configuration, enabled at boot, prebuilt by the team).
- REQ-2 (US-1): Creating a load balancer applies the 001 creation rules: bootstrap of 001 REQ-30 (backend key, password login disabled, new machine-id and SSH host keys, hostname = name), precondition checks and cleanup of 001 REQ-31 (with "Disco base de HAProxy no encontrado" when `APP_HAPROXY_BASE_DISK` does not exist), and the single-creation rule of 001 REQ-32 shared with 001 VM creation. The bootstrap authenticates as root with the same `APP_GUEST_PASSWORD_FILE` of 001 REQ-22, under the same rules; the HAProxy base disk has the same root password as the 001 base disk.
- REQ-3 (US-1): A load balancer has two adapters: adapter 1 bridged to `APP_BRIDGE_ADAPTER` (DHCP from the LAN, as in 001 REQ-1) and adapter 2 attached to its own VirtualBox internal network `stratus-<lb>`. Creation creates that network with a DHCP server on the lowest free subnet `10.10.N.0/24` (N 1-254; a subnet is free when no load balancer registered in the app and no existing VirtualBox DHCP server uses it), gives the load balancer the fixed address `10.10.N.1/24` on adapter 2 and leases `10.10.N.10`-`10.10.N.200` to servers. When all 254 subnets are used, creation fails with "No hay subredes internas libres" and registers nothing. When `stratus-<lb>` already has a DHCP server in VirtualBox, creation fails with "Red interna ya registrada en VirtualBox" and registers nothing.
- REQ-4 (US-1): The bootstrap also creates the account `jump` on the load balancer as a system account (UID below 1000, `useradd --system`), so 002 neither lists nor deletes it: no password, no login shell, SSH allowed only with keys and only for forwarding connections to port 22 of addresses in its internal network `10.10.N.0/24` (no command execution, no shell, no forwarding to other networks or to other ports). The bootstrap adds the backend's public key to `jump`'s `authorized_keys` with the same limits, so the backend can jump as `jump` (REQ-19).
- REQ-5 (US-1): Load balancers appear in the 001 VM selector with a "Balanceador" label, so every 001, 002 and 003 operation works on them; the module screen lists only load balancers with name, state, bridged IPv4 ("-" when off), internal subnet, frontend port and server count. On a load balancer, removing haproxy from 001 is rejected with "No se puede eliminar haproxy: el balanceador lo usa", and installing ufw from 001 also allows the current frontend port (supersedes 001 REQ-25 for load balancers).
- REQ-6 (US-1): Deleting a load balancer follows 001 REQ-3 after confirmation, and also removes its internal network and DHCP server. It is rejected with "Quite primero los servidores del balanceador" while it has at least one server, and changes nothing. The same rules apply when a load balancer is deleted from the 001 screen (supersedes 001 REQ-3 for load balancers).
- REQ-7 (US-3): Each load balancer has exactly one frontend, listening on all its addresses on a port 1-65535 other than 22 (default 80), and one backend with roundrobin balancing and a health check on every server. A new load balancer starts with frontend port 80 and no servers. Saving the port rewrites the frontend and reloads HAProxy, and keeps the new port allowed by ufw; with 0 servers HAProxy answers 503.
- REQ-8 (US-2): The user can assign to a load balancer any registered VM that is not a load balancer and not assigned to another load balancer, with a port 1-65535 (default 80); a load balancer holds at most 10 servers ("El balanceador ya tiene 10 servidores"). A VM not allowed, including a VM already assigned to the same load balancer, is rejected with "La VM no se puede asignar a este balanceador" and nothing changes.
- REQ-9 (US-2): Each server is named `server<N>` in the backend, using the lowest free N starting at 1 within its load balancer; the VM name and hostname do not change.
- REQ-10 (US-2): Assigning a server, after a confirmation that warns the VM restarts: stops the VM (001 REQ-3 stop rules), attaches adapter 1 to `stratus-<lb>`, adds adapter 2 as NAT for outbound internet without port forwarding, starts it, waits up to 120 seconds for its internal IPv4, copies its public keys to `jump` (REQ-17), adds the server line to the backend and reloads HAProxy. After a successful assign the VM is left running, even if it was powered off before. If any step fails, the VM gets its bridged adapter back without the NAT adapter, its previous power state is restored, the backend and `jump` keys are left as before, and the UI shows the failure. For an assigned server this supersedes the single bridged adapter of 001 REQ-1 and AC-26.
- REQ-11 (US-2): Removing a server, after a confirmation that warns the VM restarts: removes its line from the backend and reloads HAProxy, removes its keys from `jump` (REQ-17), stops the VM, removes the NAT adapter, attaches adapter 1 to `APP_BRIDGE_ADAPTER` again and starts the VM only if it was running. Removing a server already gone from the backend or from `jump` succeeds. When its load balancer is off or reports no bridged IPv4, removal fails with "El balanceador <lb> está apagado; enciéndalo para llegar al servidor" and changes nothing; the user must start the load balancer first.
- REQ-12 (US-2): Deleting a VM in 001 is rejected with "La VM es servidor de un balanceador; quítela primero" while it is assigned (supersedes 001 REQ-3 for assigned VMs).
- REQ-13 (US-4): A server's IP is its IPv4 on the internal network `stratus-<lb>` as reported by Guest Additions; 001 lists that address for the VM (supersedes 001 REQ-2 for assigned servers).
- REQ-14 (US-4): After every successful 001 start of a server or of a load balancer, and when the user clicks "Actualizar IPs" on a load balancer, the backend runs the refresh script for that load balancer: it waits for all running servers in parallel, in one shared window of at most 120 seconds, for each to report an internal IPv4 (a server without an IP when the window ends is handled by REQ-15), rewrites every server line with its current IP and port, and reloads HAProxy only if the backend changed. When a 001 start succeeds but its automatic refresh fails or is rejected (for example, the load balancer is off or locked, or the HAProxy check fails), the start is reported as a success, the refresh is recorded as its own failed row in the 004 history, and the UI shows the warning "VM iniciada; no se pudieron actualizar las IPs del balanceador <lb>, use Actualizar IPs".
- REQ-15 (US-4): A server that is off or reports no internal IPv4 when the backend is rewritten keeps its line with its last known IP and the `disabled` flag, so HAProxy sends it no traffic; the next refresh with an IP enables it again.
- REQ-16 (US-2..US-4): Every change to haproxy.cfg is checked with HAProxy's configuration check before reloading; a failed check keeps the previous file and running configuration, and the UI shows "Configuración de HAProxy inválida; se mantuvo la anterior" with the check output in the history stderr. When the check passes but the reload fails (for example, the frontend port is already in use on the load balancer), the previous haproxy.cfg is restored and HAProxy is reloaded with it, the operation fails with "No se pudo recargar HAProxy; se mantuvo la configuración anterior", and the reload output goes to the history stderr.
- REQ-17 (US-6): On assign, every public key in root's and regular users' (002 REQ-1) `authorized_keys` of the server, except the backend key, is added to `jump`'s `authorized_keys` on its load balancer; on remove, those keys are removed. The backend key in `jump` (REQ-4) is never removed by these operations. A key generated on an assigned server by 001 US-3 or 002 US-2 is also added to `jump`; deleting a user (002 US-3) removes its key from `jump`. If updating `jump` fails in any of these 001 or 002 operations, the change on the server is rolled back and the UI shows the failure.
- REQ-18 (US-6): For a VM assigned as server, the private key usage messages of 001 REQ-9 and 002 REQ-11 show the jump command `ssh -J jump@<LB bridged IPv4> -i <key file> <user>@<server internal IPv4>` instead of the direct command (supersedes the commands of 001 REQ-9 and 002 REQ-11 for assigned servers). Accounts without a key cannot connect by SSH (P4, 001 REQ-30).
- REQ-19 (US-6): Every SSH operation of 001, 002 and 003 on a server reaches it through a jump on its load balancer as `jump` with the backend key (`ssh -J jump@<LB bridged IPv4> root@<server internal IPv4>`); when the load balancer is off or reports no bridged IPv4, the operation fails with "El balanceador <lb> está apagado; enciéndalo para llegar al servidor" and runs no remote command; when the load balancer is on but the server is off or reports no internal IPv4, the operation fails with the 001 REQ-29 message "La VM no tiene dirección IP; verifique que esté encendida" and runs no remote command. For assigned servers this supersedes the direct SSH target `<VM IPv4>:22` of 001 REQ-24, 001 REQ-29, 002 REQ-17 and 003 REQ-26.
- REQ-20 (US-5): The module screen shows, for the selected load balancer, a servers table with name (`server<N>`), VM, internal IPv4, port and HAProxy state (`UP`, `DOWN` or `MAINT`, as reported by HAProxy), read from the load balancer at each load and after each operation. A successful read shows the toast "Estado del balanceador actualizado"; a failed read shows the usual failure message. When the selected load balancer is off, no read runs: the table shows the servers stored by the app (name, VM, last known IP, port) with state "-" and a note that the load balancer is off, and no failure toast appears.
- REQ-21 (US-1..US-6): Operations that change a load balancer and one of its servers (assign, remove, and on an assigned server 001 key generation, 002 user creation and 002 user deletion) hold the per-VM lock (001 REQ-15) of both; refresh, save frontend and read state hold the load balancer's lock; a second request on a locked VM is rejected with "Operación en curso en esta VM" (supersedes the one-VM lock of 001 REQ-15 for these two-VM operations).
- REQ-22 (US-1..US-6): Every operation is executed by its own script file with a 15-minute timeout (001 REQ-14); every operation ends with a success or failure message; failure messages are understandable and do not show raw stack traces; while an operation runs, the UI shows a loading indicator and disables the buttons.
- REQ-23 (US-7): Create, delete, assign, remove, save frontend and refresh are always recorded; read state is recorded only when it fails. Each row has operation name, VM, command and arguments, exit code, stderr, result and timestamp; no private key is recorded. For assign and remove, the VM column records the load balancer and the server VM appears in the arguments column (for example VM `lb1`, arguments `assign web-a 80`).
- REQ-24 (US-7): The module screen shows the last 50 recorded operations of the module; each row can expand to show its stderr.
- REQ-25 (US-1..US-7): The home card "Backends HAProxy" is enabled and navigates to the module screen (supersedes the "Próximamente" state of 001 REQ-19, 002 AC-27 and 003 AC-35 for this card).
- REQ-26 (US-1..US-6): Each script file starts with a header documenting usage, arguments and exit-code table (including reserved code 99 "Operación no implementada"), followed by `set -euo pipefail`, with comments organized in sections and numbered steps.
- REQ-27 (US-1..US-7): The UI is built with shadcn/ui components and all its text is in Spanish.

## 5. Acceptance criteria
- AC-1 (US-1): Given valid name, memory and CPUs, when the user submits "Crear balanceador", then the create script is invoked with them as separate arguments and the UI shows the result.
- AC-2 (US-1): Given an invalid or duplicate name, or memory or CPUs out of range, when the user submits, then the UI shows the 001 validation message and no script is invoked.
- AC-3 (US-1): Given `APP_HAPROXY_BASE_DISK` points to a missing file, when the user creates a load balancer, then the UI shows "Disco base de HAProxy no encontrado" and no VM or internal network is registered.
- AC-4 (US-1): Given a load balancer created, when its configuration is inspected, then its disk is a differencing child of `APP_HAPROXY_BASE_DISK`, adapter 1 is bridged to `APP_BRIDGE_ADAPTER`, adapter 2 is on `stratus-<lb>`, and that network has a DHCP server leasing `10.10.N.10`-`10.10.N.200`.
- AC-5 (US-1): Given load balancers on `10.10.1.0/24` and `10.10.3.0/24`, when a new one is created, then it gets `10.10.2.0/24`.
- AC-6 (US-1): Given a load balancer created, when it is inspected over SSH, then the 001 bootstrap state holds (AC-40 of 001), HAProxy is active, adapter 2 has `10.10.N.1/24`, and `jump` has no password and no login shell, and its `authorized_keys` holds the backend key with forwarding limited to port 22 in `10.10.N.0/24`.
- AC-7 (US-1): Given a creation whose bootstrap fails, when it finishes, then the UI shows a failure, and the VM, its differencing disk and its internal network no longer exist, and `APP_HAPROXY_BASE_DISK` is unchanged.
- AC-8 (US-1): Given a 001 VM creation in progress, when the user creates a load balancer, then the UI shows "Ya hay una creación de VM en curso" and no script is invoked.
- AC-9 (US-1): Given load balancer `lb1`, when the user opens the 001 prepare screen, then `lb1` is in the selector with the "Balanceador" label, and setting its hostname works as for any VM.
- AC-10 (US-1): Given a load balancer with one server, when the user confirms delete, then the UI shows "Quite primero los servidores del balanceador" and nothing changes; given it has no servers, then the VM, its disk and its internal network are removed.
- AC-11 (US-3): Given a load balancer, when the user saves frontend port 8080, then HAProxy listens on 8080 and no longer on the previous port; given port 22, 0 or 65536, the form shows a validation error and no script is invoked.
- AC-12 (US-3): Given a load balancer with no servers, when a client requests `http://<LB bridged IPv4>:<frontend port>/`, then HAProxy answers 503.
- AC-13 (US-2): Given a running VM `web-a` on the bridge and a load balancer `lb1` with no servers, when the user assigns `web-a` with port 80 and confirms, then `web-a` restarts with adapter 1 on `stratus-lb1` and adapter 2 as NAT, gets an address in `10.10.N.10`-`10.10.N.200`, the backend has `server1` with that address and port 80, and the UI shows the result.
- AC-14 (US-2): Given `server1` and `server2` assigned and the user removes `server1`, when another VM is assigned, then it is named `server1`.
- AC-15 (US-2): Given a VM that is a load balancer, is assigned to another load balancer, or a load balancer with 10 servers, when the user assigns, then the UI shows the matching message of REQ-8 and nothing changes.
- AC-16 (US-2): Given a server port of 0, 65536 or `80a`, when the user submits, then the form shows a validation error and no script is invoked.
- AC-17 (US-2): Given an assign whose VM reports no internal IPv4 within 120 seconds, when the operation ends, then the UI shows a failure, the VM is back on the bridge without NAT adapter in its previous power state, and the backend and `jump` keys are unchanged.
- AC-18 (US-2): Given an assigned server that was running, when the user removes it and confirms, then its line is gone from the backend, its keys are gone from `jump`, the VM runs again on the bridge with only adapter 1 and gets a LAN IPv4.
- AC-19 (US-2): Given an assigned server, when the user deletes it in 001, then the UI shows "La VM es servidor de un balanceador; quítela primero" and nothing changes.
- AC-20 (US-2, US-4): Given a server with outbound access through its NAT adapter, when the user installs `nginx` on it from 001, then the install succeeds.
- AC-21 (US-4): Given `server1` at `10.10.1.11`, when the VM is stopped, its lease changes and it is started from 001, then after the start the backend line for `server1` has its new address and HAProxy was reloaded.
- AC-22 (US-4): Given a load balancer whose servers' addresses did not change, when the user clicks "Actualizar IPs", then the operation succeeds and HAProxy is not reloaded.
- AC-23 (US-4): Given `server2` powered off, when the backend is rewritten, then its line keeps its last address with the `disabled` flag; when it starts again, its line is updated and enabled.
- AC-24 (US-2..US-4): Given a change whose resulting configuration fails HAProxy's check, when the operation runs, then haproxy.cfg and the running configuration are unchanged and the UI shows "Configuración de HAProxy inválida; se mantuvo la anterior".
- AC-25 (US-5): Given `server1` running a web server on its port and `server2` with nothing listening on its port, when the user opens the module screen, then the table shows `server1` `UP` and `server2` `DOWN`.
- AC-26 (US-6): Given a server with a root key generated by 001 before assignment, when it is assigned, then that public key is in `jump`'s `authorized_keys` once, beside the backend key added at creation; when the server is removed, that key is gone from `jump` and the backend key remains.
- AC-27 (US-6): Given an assigned server, when the user generates a root key (001) or creates a user with key (002) on it, then the UI usage message shows `ssh -J jump@<LB bridged IPv4> -i <key file> <user>@<server internal IPv4>`, the public key is added to `jump`, and that command opens a session on the server.
- AC-28 (US-6): Given a key in `jump`, when it is used to open a shell or run a command on the load balancer, or to forward to an address outside `10.10.N.0/24` or to a port other than 22 inside it (for example `10.10.1.11:3306`), then the connection is refused.
- AC-29 (US-6): Given an assigned server and its load balancer powered off, when the user installs a package on the server, then the UI shows "El balanceador <lb> está apagado; enciéndalo para llegar al servidor" and no remote command runs.
- AC-30 (US-1..US-4): Given the real host, when a load balancer with two servers running a web server is demonstrated, then repeated requests to the frontend port are answered by both servers in turn (before: no load balancer; after: balanced responses).
- AC-31 (US-4): Given the real host, when a server is restarted and its address changes, then requests through the frontend still reach it after the restart.
- AC-32 (US-6): Given the real host, when the user runs the jump command from AC-27 with the downloaded key, then a root or user session opens on the server.
- AC-33 (US-1): Given the real host, when a load balancer without servers is deleted, then `VBoxManage list intnets` and the DHCP servers no longer include `stratus-<lb>`.
- AC-34 (US-1..US-6): Given an assign running on `lb1` and `web-a`, when another operation is requested on `lb1` or `web-a`, then it is rejected with "Operación en curso en esta VM".
- AC-35 (US-7): Given more than 50 recorded operations, when the user opens the module screen, then only the 50 most recent are listed, newest first; a successful state read adds no row.
- AC-36 (US-1..US-7): Given the home screen, when it loads, then the "Backends HAProxy" card navigates to the module screen.
- AC-37 (US-1..US-6): Given a script run directly with a missing argument or a value outside its allowlist (for example frontend port `22`), when it runs, then it exits with code 2 and calls neither VBoxManage nor ssh.
- AC-38 (US-1..US-6): Given the script files, when one is opened, then it contains usage, arguments, exit-code table (including 99), `set -euo pipefail` and comments with sections and numbered steps.
- AC-39 (US-4): Given a load balancer with 10 running servers, when the refresh runs, then it waits for all of them in parallel for at most 120 seconds in total, and every server without an internal IPv4 at the end keeps its last address with the `disabled` flag.
- AC-40 (US-2): Given an assigned server and its load balancer powered off, when the user confirms removing the server, then the UI shows "El balanceador <lb> está apagado; enciéndalo para llegar al servidor", and the VM's adapters and power state, haproxy.cfg and `jump`'s keys are unchanged.
- AC-41 (US-4): Given an assigned server whose load balancer is off, when the user starts the server from 001, then the start succeeds, the 004 history has a failed refresh row, and the UI shows "VM iniciada; no se pudieron actualizar las IPs del balanceador <lb>, use Actualizar IPs".
- AC-42 (US-6): Given an assigned server `web-a` of `lb1` and an operation running on `lb1`, when the user generates a root key on `web-a` (001) or creates or deletes a user on it (002), then it is rejected with "Operación en curso en esta VM"; given the `jump` update fails during such an operation, then the change on `web-a` is rolled back and the UI shows the failure.
- AC-43 (US-1): Given load balancer `lb1` with one server, when the user deletes it from the 001 screen, then the UI shows "Quite primero los servidores del balanceador" and nothing changes; given it has no servers, then the VM, its disk, `stratus-lb1` and its DHCP server are removed.
- AC-44 (US-1): Given a load balancer created, when it is inspected, then `jump` has a UID below 1000, and when it is selected in 002, then `jump` is not listed.
- AC-45 (US-3): Given `nginx` listening on port 8080 on a load balancer with frontend port 80, when the user saves frontend port 8080, then the UI shows "No se pudo recargar HAProxy; se mantuvo la configuración anterior", haproxy.cfg is the previous one, HAProxy still listens on 80, and the history stderr holds the reload output.
- AC-46 (US-5): Given load balancer `lb1` powered off with `server1` (VM `web-a`, last IP `10.10.1.11`, port 80), when the user selects it on the module screen, then no read runs, the table shows `server1 | web-a | 10.10.1.11 | 80 | -` with a note that the load balancer is off, and no failure toast appears.
- AC-47 (US-6): Given an assigned server powered off and its load balancer running, when the user installs a package on the server, then the UI shows "La VM no tiene dirección IP; verifique que esté encendida" and no remote command runs.
- AC-48 (US-2): Given a powered-off VM `web-a`, when it is assigned to `lb1` successfully, then `web-a` is left running; when the user assigns `web-a` to `lb1` again, then the UI shows "La VM no se puede asignar a este balanceador" and nothing changes.
- AC-49 (US-1): Given a load balancer, when the user removes haproxy from it in 001, then the UI shows "No se puede eliminar haproxy: el balanceador lo usa" and nothing changes; given frontend port 80, when the user installs ufw on it in 001, then 22/tcp and 80/tcp are allowed; when the user then saves frontend port 8080, then 8080/tcp is allowed.
- AC-50 (US-1): Given a VirtualBox DHCP server on `10.10.1.0/24` not registered in the app, when a load balancer is created, then it gets `10.10.2.0/24`; given `stratus-lb1` already has a DHCP server in VirtualBox, when the user creates `lb1`, then the UI shows "Red interna ya registrada en VirtualBox" and nothing is registered.
- AC-51 (US-7): Given an assign of `web-a` to `lb1` with port 80, when the history is inspected, then the row has VM `lb1` and the arguments include `web-a` and `80`.

## 6. Out of scope
- More than one frontend or backend per load balancer; choosing the balancing algorithm; HTTP rules, ACLs or sticky sessions.
- TLS termination and certificates.
- The HAProxy stats web page.
- Renaming VMs or hostnames to `server<N>`.
- One internal network shared by several load balancers; static IPs for servers; IPv6.
- Assigning a load balancer as a server of another load balancer.
- Building the HAProxy base disk (the team prepares it by hand once: Debian 13, Guest Additions, openssh-server, HAProxy with basic configuration, root password).
- SSH jump for accounts without a key.
- Periodic IP polling; IP changes while a VM keeps running (lease renewals with a new address).

## 7. Clarifications
- 2026-10-24. Q: How do servers join a load balancer? A: The user assigns existing 001 VMs; the app moves adapter 1 to the internal network; they are named `server<N>` only in haproxy.cfg.
- 2026-10-24. Q: Servers on an internal network have no internet; how do they install packages? A: Each server gets a second NAT adapter for outbound internet only; SSH still goes through the load balancer.
- 2026-10-24. Q: When are server IPs refreshed? A: After every successful start of a server or its load balancer, and with the "Actualizar IPs" button.
- 2026-10-24. Q: HAProxy configuration scope? A: One frontend (port 1-65535 except 22, default 80) and one roundrobin backend with health checks per load balancer.
- 2026-10-24. Q: How is a load balancer created? A: "Crear balanceador" form in the module screen, cloning `APP_HAPROXY_BASE_DISK` with the 001 bootstrap; it appears in every VM selector.
- 2026-10-24. Q: How does the user SSH into a server? A: Through a `jump` account on the load balancer, with no shell and forwarding only; server public keys are copied to it.
- 2026-10-24. Q: Internal network scope? A: One internal network per load balancer, with its own DHCP and `/24` subnet, created and deleted with the load balancer.
- 2026-10-24. Q: Removing servers and deleting load balancers? A: Removing a server puts it back on the bridge without NAT adapter; deleting a load balancer with servers is rejected; deleting an assigned VM in 001 is rejected.
- 2026-10-24. Q: Show live server state? A: Yes, `UP`, `DOWN` or `MAINT` as reported by HAProxy.
- 2026-10-24. Q: Server off or without IP when the backend is rewritten? A: Its line keeps the last IP with the `disabled` flag until a refresh finds an IP.
- 2026-10-24. Q: Assigning needs a power cycle; how? A: The app stops, reconfigures and starts the VM after a confirmation; removal does the same.
- 2026-10-24. Q: Server limits and naming? A: 0 to 10 servers per load balancer; names use the lowest free number.
- 2026-10-24. Q: What does "connect via SSH only if login is disabled because of a set key" mean? A: The jump works only for accounts with key access; password SSH login stays disabled everywhere (P4).
- 2026-10-24. Q: The refresh waits up to 120 s per server; with 10 servers that exceeds the 15-minute timeout; how should the wait work? A: One shared 120 s window for all running servers, waited in parallel; any server without an IP after it gets the `disabled` flag.
- 2026-10-24. Q: How can the user release servers when their load balancer is off or cannot boot? A: Removal fails with "El balanceador <lb> está apagado; enciéndalo para llegar al servidor" and changes nothing; the user must start the load balancer first.
- 2026-10-24. Q: Which root password file does the HAProxy base disk use for the bootstrap? A: The same `APP_GUEST_PASSWORD_FILE`; both base disks share the same root password.
- 2026-10-24. Q: How are the changes to approved specs 001-003 recorded? A: Only in 004: section 2 "Conflicts" and each affected REQ name the 001-003 requirement they supersede; 001-003 stay unchanged.
- 2026-10-24. Q: What happens when a 001 start succeeds but its automatic refresh fails or is rejected? A: The start is reported as a success; the refresh is recorded as its own failed row in the 004 history; the UI shows "VM iniciada; no se pudieron actualizar las IPs del balanceador <lb>, use Actualizar IPs".
- 2026-10-24. Q: Which locks do 001 key generation and 002 user create or delete take on an assigned server, and what if the `jump` update fails? A: They hold the locks of both the server and its load balancer; if the `jump` update fails, the server change is rolled back and the UI shows the failure.
- 2026-10-24. Q: How does a delete from the 001 screen behave for a load balancer? A: It follows REQ-6: rejected with "Quite primero los servidores del balanceador" while it has servers; otherwise it also removes its internal network and DHCP server.
- 2026-10-24. Q: What kind of account is `jump`? A: A system account (UID below 1000, `useradd --system`), so 002 neither lists nor deletes it.
- 2026-10-24. Q: What happens when the HAProxy check passes but the reload fails (for example, a port in use)? A: The previous haproxy.cfg is restored and HAProxy is reloaded with it; the operation fails with "No se pudo recargar HAProxy; se mantuvo la configuración anterior"; the reload output goes to the history stderr.
- 2026-10-24. Q: What does the servers table show when the selected load balancer is off? A: No read runs; the table shows the stored servers (name, VM, last known IP, port) with state "-" and a note that the load balancer is off; no failure toast.
- 2026-10-24. Q: Which message is shown when the load balancer is on but the server is off or has no internal IPv4? A: The 001 REQ-29 message "La VM no tiene dirección IP; verifique que esté encendida", and no remote command runs.
- 2026-10-24. Q: Power state after assigning a powered-off VM, and reassigning to the same load balancer? A: The VM ends running after a successful assign; reassigning a VM to the same load balancer is rejected with "La VM no se puede asignar a este balanceador".
- 2026-10-24. Q: Should `jump` forwarding be narrower than any port in `10.10.N.0/24`? A: Only port 22 of addresses in `10.10.N.0/24`; tunnels to other ports are refused.
- 2026-10-24. Q: Should 001 protect load balancers? A: Removing haproxy is rejected with "No se puede eliminar haproxy: el balanceador lo usa"; installing ufw also allows the current frontend port; a frontend save keeps the new port allowed.
- 2026-10-24. Q: What counts as a free subnet, and what if `stratus-<lb>` already has a DHCP server in VirtualBox? A: Free means not used by any load balancer registered in the app nor by any existing VirtualBox DHCP server; an existing `stratus-<lb>` DHCP server makes creation fail with "Red interna ya registrada en VirtualBox" and registers nothing.
- 2026-10-24. Q: Which VM does the history record for assign and remove? A: The load balancer, with the server VM in the arguments column (for example VM `lb1`, arguments `assign web-a 80`).
- 2026-10-24. Q: Which account on the load balancer does the backend jump through? A: `jump`: the backend key is also added to `jump`'s `authorized_keys` with the same port-22-only forwarding limits, and the backend jumps with `ssh -J jump@<LB bridged IPv4> root@<server internal IPv4>`.
- 2026-10-24. Q: When does the backend key enter `jump`? A: During the load balancer bootstrap (REQ-4).
